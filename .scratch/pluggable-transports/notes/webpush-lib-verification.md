# Spike 03 — web-push library verification (Go/No-Go)

**Verdict: Go.** A real `web-push@4.0.0` POST over TLS was captured on a local endpoint and its payload decrypted byte-exact per RFC 8291 with the receiver-held key, under both Node and Bun — the exact sender-side path the Web Push adapter (tickets 04/05) depends on works as-is.

- Date: 2026-11-15
- Branch: `ticket/03-webpush-spike` (at integration tip 2a697b9). Spike only — no product code, no dependency changes (`package.json`/`bun.lock` untouched; library installed `npm install --no-save`).

## Versions

| Component | Version |
|---|---|
| web-push | **4.0.0** (published 2026-11-06; deps: http_ece 1.2.1, jws 4.0.1, asn1.js ^5.3.0, https-proxy-agent ^9.1.0) |

## What was verified

Harness (uncommitted): `.scratch/pluggable-transports/spike/harness.mjs`, raw outputs `result-node.json`, `result-bun.json` in the same folder. 14/14 checks pass on both runtimes.

1. **VAPID key generation via documented tooling** — `npx web-push generate-vapid-keys --json` produces a 65-byte uncompressed P-256 public key and 32-byte private key; `generateVAPIDKeys()` (programmatic) likewise.
2. **Verified local endpoint** — HTTPS server on `127.0.0.1` (ephemeral port, self-signed cert); subscription's `p256dh`/`auth` keys generated by the harness (createECDH('prime256v1'), random 16-byte auth secret); `webpush.sendNotification(sub, payload, { vapidDetails, TTL: 3600, contentEncoding: 'aes128gcm' })` sends a real TLS 1.3 POST (`socket.encrypted=true`, 201 response).
3. **RFC 8291 decryption (the core proof)** — captured request body decrypted with an independent from-spec implementation using only the harness-held receiver private key: ECDH P-256 with the sender's ephemeral key (embedded in the `keyid` header field), HKDF-SHA256 (`"WebPush: info\0"` + receiver∥sender → 32-byte IKM; salt → PRK; `"Content-Encoding: aes128gcm\0"` / `"...nonce\0"` → 16/12-byte key/nonce — precisely per RFC 8291 §4: the salt of the shared-secret HKDF is the authentication secret (auth), and the auth secret is likewise the input keying material of the key/nonce HKDF, whose salt is the 32-byte IKM from step 1; verified byte-exact against http_ece), AES-128-GCM with **zero-length AAD** and delimiter-octet padding per RFC 8188. Decrypted plaintext === payload sent, exactly.
4. **Cross-check** — the library's own crypto engine (`http_ece.decrypt`, version 'aes128gcm') agrees byte-for-byte.
5. **VAPID JWT** — Authorization header is `vapid t=<JWT>, k=<pub>`; JWT is `alg:ES256`, `aud` = endpoint origin, `sub` = configured mailto, `exp` = +12 h; ES256 signature verifies against the generated VAPID public key; `k=` equals the public key. Wire also shows `Content-Encoding: aes128gcm`, `Content-Type: application/octet-stream`, `TTL` — and *no* legacy `Encryption`/`Crypto-Key` headers, i.e. the RFC 8291 (not draft) encoding, which is the default in both majors (3.6.7 line 111 / 4.0.0 line 106).

## Node vs Bun findings

- **Identical result: 14/14 PASS on both.** No crypto, HKDF, ECDH, AES-GCM, JWT (incl. `dsaEncoding: 'ieee-p1363'` verify) or https-server differences of substance.
- Cosmetic: Bun's TLSSocket does not implement `getProtocol()`/`getCipher()` (return `null`); TLS itself works.
- ESM import of the CJS package: `(await import('web-push')).default` is `undefined`; use the namespace object (`ns.generateVAPIDKeys`) or `require()`. Trivial workaround for plugin code.
- No workarounds needed for the happy path.

## Constraints / risks that shape tickets 04/05

- **HTTPS-only sender**: web-push 4.0.0 hard-codes `https.request` — a plain-`http://` endpoint cannot be used (also blocks trivial local testing). Real push services are HTTPS anyway; the bootstrap service (05) only needs to sit behind the user's TLS reverse proxy. For tests, `options.agent` (must be an `https.Agent` instance) is honored — self-signed local endpoints work with `rejectUnauthorized: false`.
- **Pin the version**: 4.0.0 is a fresh major (2026-11-06) that swapped the crypto engine to `http_ece@1.2.1`. Wire format verified identical to 3.6.7 (that version also passes the full harness, same RFC 8188 aes128gcm), so `3.6.7` is a proven fallback if 4.0.0 regresses. Recommend pinning exact (`web-push@4.0.0`) in ticket 04.
- `sendNotification` expects the payload as string/Buffer; the adapter must `JSON.stringify` itself (no auto-serialization).
- Nothing found that challenges the ADR's choice of web-push as the sole new runtime dependency.

## How to reproduce

```sh
npm install --no-save --no-package-lock web-push      # coexists with bun-installed node_modules
npx web-push generate-vapid-keys                       # documented VAPID tooling
openssl req -x509 -newkey rsa:2048 -nodes -days 3 \
  -keyout selfsigned.key -out selfsigned.crt \
  -subj "/CN=127.0.0.1" -addext "subjectAltName=IP:127.0.0.1"
node .scratch/pluggable-transports/spike/harness.mjs   # and: bun .scratch/.../harness.mjs
```
